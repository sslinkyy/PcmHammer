# AL5 object transformation through HAPI

The callback IPC recipient is statically linked to EFILive_Hapi.exe. ScanAndTune maps EFILive_Hapi_SHM (0xC0AD bytes), synchronizes with EFILive_Hapi_SEM, and registers its receiver object with the VM callback. Hapi maps the same named object, publishes its form HWND to shared offset0 at 0xA52615, and its TfMainHapi dynamic-method table binds message0x8000 to WMEfiHapi at0xA53C9C. Framework lookup instructions corroborate this binding. This does not observe live window ownership or execution.

The Hapi handler routes selectors12/13 through device selection and A16CC8/A170DC send/receive helpers. The send helper's branch2 forms a0154 host-interface wrapper and reaches an indirect transport call; an alternative branch3 uses another device dispatch. The device transformation algorithm and firmware response production remain unknown. Calling EFILive or its callback is not required by the offline tools.

VM helper0x403060 initializes each section with command0x8414 and34bytes: selector12 for code,13 for data, zero second byte and32 generated bytes. It submits command0x8415 chunks of at most4096bytes, then applies local helper0x40BD8C to the replies. The local helper uses little-endian words,13 left steps with key0x958E3535 (conditional XOR before doubling and setting bit0), then XOR with byte-swapped key0x35358E95 and the chunk-local word index. The index restarts for every chunk.

All five saved AL5_W.htx files contain16 complete transform wrappers each: two initialization request/reply pairs and six chunk request/reply pairs. Exact transmitted code and data bytes match installed AL5_W.obj. The code section input chunks are4096,4096,1472 bytes; the data chunks are4096,4096,3216. Strict offline replay of the recorded replies plus the local word transform yields the expected validator CRC0xFCA1 in every trace. Data buffer hashes match across all five replays; full code buffer hashes differ. The reports retain those differences without claiming identical objects.

Tools/AL5/audit_object_transforms.py inventories every supplied binary record, including malformed transform signatures without promoting them to messages. Tools/AL5/replay_object_transform.py requires caller-pinned trace/object hashes, exact transmitted section bytes, selector/chunk sequence and reply lengths. Missing, extra, malformed, repeated or reordered exchanges are rejected. Only hashes, counts, provenance and validation results are exported; no decoded buffers or executable packets are emitted.

This reproduces a captured exchange using its saved device replies. It does not decode arbitrary object files independently. Wrapper checksums, response status semantics, date compatibility, successful full VM validation, object execution, programming and interrupted-programming recovery remain unverified. The CRC tool excludes code48..63 as observed by the validator. A CRC match cannot promote any write gate.

Evidence: EFILIVE_HOST_IPC.json retains static source hashes, VA/RVA/file mappings, bounded disassembly and REA transform records. OBJECT_TRANSFORM_TRACE_AUDIT.json retains all80 wrapper observations; OBJECT_TRANSFORM_REPLAY.json retains five pinned replay reports. Existing E54 and AL5 Mode0x23 paths are unchanged.
